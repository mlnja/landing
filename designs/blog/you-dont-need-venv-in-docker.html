You don't need venv in Docker.

Dmitry Rubinstein
Jun 12, 2025 · 7 min read
#docker #containers #python #venv #uv #packaging #deployment
[ hero illustration — sad whale carrying a -venv folder ]
Illustration by team

Let's be blunt.

If your Dockerfile starts with python -m venv, you've already taken a wrong turn.

This may feel controversial, but it shouldn't be: in 2025, we have better tools and a clearer mental model of what a container actually is. The TL;DR — the container is the environment. You don't need another one inside it.

Why people reach for venv in Docker

It's muscle memory. Outside Docker, virtual environments protect you from the host's Python, your other projects, and the seventeen abandoned pip installs you forgot you ran in 2022. Reaching for venv is the first thing most Python developers do on a new machine.

So when the same developer writes their first Dockerfile, the muscle takes over. FROM python:3.12, python -m venv /venv, ENV PATH=/venv/bin:$PATH. Off to the races.

The problem is that none of the reasons you wanted a venv on your laptop apply inside a container.

What you're actually protecting against

A venv protects you from three things:

  1. The system Python installation shared with other tools.
  2. Other projects on the same machine with different dependencies.
  3. Your own accumulated cruft over years on the same box.

Inside a Docker image, none of these exist. There is no other project. There is no system Python you care about — the image is the system, and you control it. And there is no cruft, because the image is built from scratch every time.

The container is the venv. Adding a second one is a tax on every developer who has to read your Dockerfile. — a thing we say in code review

The four-line Dockerfile

Here's what we actually use on most Python services:

DockerfileFROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "-m", "app"]

Six lines, but the four that matter are WORKDIR, COPY, RUN pip install, and COPY. No venv, no PATH manipulation, no two-stage dance.

Want it reproducible? Pin your requirements. Want it small? Switch to python:3.12-alpine or a distroless base. Want it fast to build? Use uv instead of pip — same model, just faster:

DockerfileFROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
WORKDIR /app
COPY pyproject.toml uv.lock .
RUN uv sync --frozen --no-install-project
COPY . .
RUN uv sync --frozen
CMD ["uv", "run", "app"]

Notice what's still missing: the venv. uv sync manages its own environment under the hood; you don't activate anything. The container is still the environment.

!
When you do need it

There's one case where we relent: multi-stage builds where you want to copy a fully resolved environment from a builder stage to a distroless final image. In that narrow case, a venv is a portable directory of dependencies you can COPY --from=builder. It's a packaging trick, not an isolation tool.

The actual cost of leaving it in

"It works, who cares?" Fair question. Three reasons we care:

  • Build time. Creating the venv is a wasted layer. Activating it requires ENV PATH manipulation that confuses every linter and IDE that reads your Dockerfile.
  • Cognitive load. The next person to read your image sees /venv/bin/python and wonders what they're insulated from. Spoiler: nothing.
  • Cargo cult. Once one project does it, every project does it. We've audited deployments where four of the seven services had different venv setups for no defensible reason.

What to do instead

Delete the venv. Pin your requirements. If you've got a complex build with native dependencies, use a multi-stage build to separate compile from runtime. If you want speed, use uv. If you want safety, run as a non-root user and use a distroless base.

None of that needs python -m venv. None of it ever did.
